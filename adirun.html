Context

When Runtastic closed, support for the Running app stopped scaling.

The old journey was help pages, a rule-based chatbot, then an email ticket. After Runtastic was discontinued, adidas Running support cases surged into a model that was never built for that load.

Problem

Customers waited days for help, and costs kept growing.

Support for the Running app had merged into adidas’ global Customer Service. Shared self-help pages struggled with findability, and agents still ramping on the product meant even human-assisted resolutions were slow.

The goal was to solve problems before they became tickets. My role: find where AI could help most, design how the agent should work, and test it until it did.

Opportunity

I used support data to find where AI could create the most value.

Before designing the agent, I analyzed Salesforce and Power BI data. High pain meant many cases, rarely solved first time, low NPS, and long handling time, not volume alone.

Why AI?

Customers described the same underlying issue in very different ways.

Many support cases ended in similar resolution paths, but customers worded the same problem differently every time. Scripted flows struggled with that variability. Conversational AI could interpret natural language while still following defined procedures and boundaries.

Service design

Before designing the AI, I mapped how humans actually solved the problem.

Example: “activity not counted towards challenges” required five manual steps—and could take up to 72 hours for a single case.

Those flows became the behavioural requirements for adiRun: ask for the right evidence, know the rules, check the activity in the admin tool, and explain the decision or hand off. Engineering translated the requirements into integrations and agent tools.

Designing the agent

Every new support agent gets four things. adiRun needed the same.

Like onboarding a new agent: shared behaviour, case-specific knowledge, system access, and a consistent handoff. My role was to define what each layer needed. Engineering built the knowledge stores, tools, and integrations.

01 · Instructions
Rules to follow—how it behaves. Ask for the details each case needs; apply shared rules for uncertainty. Example: “Check the facts before answering.”
02 · Knowledge
A manual—what it knows. Approved guidance per case type, kept up to date. Example: challenge rules for valid pace, distance, and GPS.
03 · Tools
System access—what it can do. Look up activities in the admin tool; take permitted actions by case type.
04 · Handoff
Someone to call—when it stops. Consistent escalation criteria; pass context to Customer Service so the runner never repeats themselves.

Together with a Content Designer, we also gave it a persona and a voice: clear, predictable, and useful—not human-sounding for its own sake.

adiRun ran in Cognigy: an LLM for understanding and generating responses, instructions and knowledge to guide behaviour, tools and handoff for actions and escalation, and a webchat endpoint in the runner’s chat. I defined the service requirements, prepared knowledge, and configured the initial instructions.

Phase 1 findings

The first version answered, but it didn’t resolve.

I built and tested the proof of concept in Cognigy against realistic support conversations. The failures were more useful than the perfect ones.

In my tests · It overstepped
Suggested stretches for a sore knee. Recommended a training plan. Filled gaps with guesses. Closed cases too early. Missing: clear rules to follow.
With 7 runners · It didn’t earn trust
They compared it to ChatGPT, not a support bot. Generic replies were dismissed even when correct. No loading indicator, so they refreshed. Conversations weren’t saved, so a refresh erased everything. Missing: facts, system access, and a real hand-off.

“I wouldn’t really have known where to wait there.” — Male, UK, 22s

“I don’t have the details of what I might be doing anymore. It could be quite a large problem there.” — Male, UK, 22s

Each failure became a rule: don’t improvise on health or training, stay grounded in what the agent knows, confirm outcomes before closing, and show the system working.

Phase 2

So we kept adding what our agents know—and what the experience needed to earn trust.

Thinking state
In testing, no loading indicator meant runners refreshed the page. I designed a “thinking” state so they know adiRun is working.
Saved conversations
A refresh erased everything. Persistent conversations meant nothing was lost.
Handoff with an AI summary
Hand-offs used to send runners to email with agents starting from zero. The new handoff passed an AI summary so Customer Service could solve it at first contact.

Solution

The second version diagnoses, takes action, confirms—or hands off with context.

adiRun asks for missing information before assuming anything, follows the same resolution logic Customer Service would use, and confirms the outcome before closing. When it can’t continue safely, it hands off to a person with the context already gathered.

Learning

Useful AI starts with the right knowledge.

I learned to organise support knowledge around user problems—so adiRun could help resolve them in chat instead of sending users back to email.
